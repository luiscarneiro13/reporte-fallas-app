CONTEXTO
La app móvil "Reporte de Fallas" necesita implementar dos flujos: reportar una
falla nueva y cerrar una falla existente. Este es el comportamiento exacto del
backend Laravel (API REST bajo /api/v1), replicado 1:1 del flujo que ya existe
en la versión web (AdminLTE) del mismo sistema.

Auth: todas las llamadas llevan header Authorization: Bearer {token} (Sanctum,
obtenido en POST /api/v1/login). Todas las respuestas usan el mismo envelope:
{ "success": bool, "message": string, "data": {...} | null, "errors": {...} }
(errors solo aparece en 422).

═══════════════════════════════════════════════════════════════════════════
PANTALLA 1: REPORTAR FALLA (crear)
═══════════════════════════════════════════════════════════════════════════

FLUJO:
1. Al entrar a la pantalla, llamar GET /api/v1/fallas/crear-datos para poblar
   los selects (ver catálogos abajo).
2. El usuario completa el formulario y envía.
3. POST /api/v1/fallas con el body de campos.
4. Éxito (201): mostrar mensaje "Falla creada" y volver a la lista.
5. Error 422: mostrar los mensajes de "errors" bajo cada campo.

PERMISO REQUERIDO: "Fallas Crear" (viene en el array `permissions` del login;
si el usuario no lo tiene, no mostrar el botón/pantalla).

ENDPOINT DE CATÁLOGOS: GET /api/v1/fallas/crear-datos
Devuelve (dentro de "data"):
- equipment: { "id": "texto" }              → dropdown Equipo
- service_area: { "id": "texto" }           → dropdown Área de servicio
- fault_status: { "id": "texto" }           → dropdown Status de la falla
  (NO incluye el estado "closed", nunca aparece como opción seleccionable)
- spare_part_status: { "id": "texto" }      → dropdown Status de repuestos
- employee_reported: { "id": "texto" }      → dropdown Reportado por
- default_fault_status_id: id|null          → ver regla de rol Operador abajo
- default_employee_reported_id: id|null     → ver regla de rol Operador abajo
(executors_internal/executors_external también vienen en esta respuesta pero
NO se usan en esta pantalla — son solo para Cerrar falla, sección 2)

CAMPOS DEL FORMULARIO (en este orden en la web):
┌─────────────────────┬──────────────────────┬──────────┬─────────────────────────────┐
│ Label                │ Campo (body)          │ Tipo     │ Requerido                    │
├─────────────────────┼──────────────────────┼──────────┼─────────────────────────────┤
│ Reportado por        │ employee_reported_id  │ select   │ Sí                           │
│ Equipo                │ equipment_id          │ select   │ Sí                           │
│ Área de servicio      │ service_area_id       │ select   │ Sí                           │
│ Status de la falla    │ fault_status_id       │ select   │ Sí                           │
│ Status de repuestos   │ spare_part_status_id  │ select   │ Sí, salvo rol Operador       │
│ Descripción de falla  │ description           │ textarea │ Sí                           │
│ Fecha del reporte     │ report_date           │ date     │ No (nullable)                │
│ Ejecución planificada │ scheduled_execution   │ date     │ No (nullable)                │
└─────────────────────┴──────────────────────┴──────────┴─────────────────────────────┘

IMPORTANTE: en esta pantalla NO existen campos de ejecutor (interno/externo),
ni "ejecución completada", ni "actividades realizadas al equipo" — esos son
exclusivos de Cerrar falla (sección 2). No los muestres acá aunque el backend
los acepte.

REGLA ESPECIAL — usuario con rol "Operador" (viene en `roles` del login):
- fault_status_id: fijo/bloqueado al valor de `default_fault_status_id`
  (no editable — ocultar el select o mostrarlo disabled con ese valor).
- employee_reported_id: precargado con `default_employee_reported_id`
  (normalmente es el propio empleado del usuario logueado).
- report_date: precargado con la fecha de hoy, campo disabled/no editable.
- spare_part_status_id: deja de ser obligatorio para este rol.
Si el usuario NO es Operador, todos los campos son editables normalmente.

REQUEST DE EJEMPLO:
POST /api/v1/fallas
{
  "employee_reported_id": 3,
  "equipment_id": 4,
  "service_area_id": 1,
  "description": "Fuga de aceite en el motor",
  "fault_status_id": 2,
  "spare_part_status_id": 1,
  "report_date": "2026-08-18",
  "scheduled_execution": "2026-08-20"
}

RESPONSE 201:
{
  "success": true,
  "message": "Falla creada",
  "data": { "id": 474, "description": "...", "equipment_name": "...", ... }
}
(el "data" trae la falla ya desnormalizada, útil si querés navegar directo al
detalle tras crear — incluye equipment_name, service_area_name, etc. ya
resueltos, no solo los ids)

═══════════════════════════════════════════════════════════════════════════
PANTALLA 2: CERRAR FALLA
═══════════════════════════════════════════════════════════════════════════

MUY IMPORTANTE: "Editar falla" y "Cerrar falla" son LA MISMA pantalla y el
MISMO endpoint (PUT /api/v1/fallas/{id}) en la web — la diferencia es un flag
`closed: true` en el body y algunos campos extra que solo aplican al cerrar.
Recomendación: para la app móvil, sí separen "Editar" de "Cerrar" en dos
pantallas/flujos distintos de UX (más claro para el usuario en mobile), pero
ambos pegan al mismo PUT, solo que Cerrar además manda `closed: true` + los
campos extra.

FLUJO (cerrar):
1. Desde la lista de fallas, el botón "Cerrar falla" solo debe aparecer en
   fallas ABIERTAS (closed_at == null en la respuesta de GET /fallas). Una
   falla cerrada no se puede volver a cerrar ni editar por este flujo.
2. Al entrar a la pantalla: GET /api/v1/fallas/{id} para traer los valores
   actuales de la falla (precargar el formulario).
3. En paralelo o después: GET /api/v1/fallas/crear-datos para los catálogos
   de los selects (mismo endpoint que en Reportar falla).
4. El usuario completa/confirma los campos y envía.
5. PUT /api/v1/fallas/{id} con `closed: true` en el body.
6. Éxito (200): la falla se archiva (se mueve a un histórico) y desaparece de
   la lista de fallas activas. Mostrar mensaje "Falla cerrada y archivada
   correctamente" y volver a la lista. La response de éxito NO trae "data".
7. Error 422: mismo manejo de "errors" que en crear.

PERMISO REQUERIDO: "Fallas Editar" (mismo permiso que editar sin cerrar).

CAMPOS DEL FORMULARIO AL CERRAR (todos los de "Reportar falla" MÁS estos, y
varios pasan a ser obligatorios):
┌─────────────────────────┬───────────────────────┬──────────┬────────────┐
│ Label                    │ Campo (body)           │ Tipo     │ Requerido  │
├─────────────────────────┼───────────────────────┼──────────┼────────────┤
│ Reportado por             │ employee_reported_id   │ select   │ Sí         │
│ Equipo                    │ equipment_id           │ select   │ Sí         │
│ Área de servicio          │ service_area_id        │ select   │ Sí         │
│ Status de la falla        │ fault_status_id        │ select   │ Sí         │
│ Status de repuestos       │ spare_part_status_id   │ select   │ Sí         │
│ Descripción de falla      │ description            │ textarea │ Sí         │
│ Fecha del reporte         │ report_date            │ date     │ Sí         │
│ Ejecución planificada     │ scheduled_execution    │ date     │ Sí         │
│ Ejecución completada  ⭐  │ completed_execution    │ date     │ Sí         │
│ Actividades realizadas ⭐ │ equipment_maintenance_log │ textarea │ Sí      │
│ Ejecutor interno      ⭐  │ executor_id            │ select   │ No         │
│ Ejecutor externo      ⭐  │ executor_external_id   │ select   │ No         │
│ (flag de cierre)          │ closed                 │ boolean  │ Sí (true)  │
└─────────────────────────┴───────────────────────┴──────────┴────────────┘
⭐ = campos que SOLO existen en el flujo de cierre, no en "Reportar falla" ni
en un "Editar" simple (sin cerrar).

CATÁLOGOS PARA LOS DOS SELECTS DE EJECUTOR (misma llamada de crear-datos):
- executors_internal: { "0": "Seleccione", "id": "cedula - Apellido Nombre" }
  → dropdown "Ejecutor interno" (campo executor_id)
- executors_external: { "0": "Seleccione", "id": "cedula/rif - Nombre" }
  → dropdown "Ejecutor externo" (campo executor_external_id)
Son catálogos DISTINTOS (personas/empresas distintas). El usuario puede
seleccionar uno, el otro, ambos, o ninguno — no son mutuamente excluyentes a
nivel de validación del backend, pero en la UI tiene sentido tratarlos como
"quién ejecutó esto: alguien interno, o un proveedor externo" — si ayuda a la
UX, se puede sugerir elegir solo uno, pero el backend no lo fuerza.
Enviar "0" (o simplemente omitir el campo) significa "sin ejecutor asignado".

REQUEST DE EJEMPLO (cerrar con ejecutor externo, sin interno):
PUT /api/v1/fallas/474
{
  "employee_reported_id": 3,
  "equipment_id": 4,
  "service_area_id": 1,
  "description": "Fuga de aceite en el motor",
  "fault_status_id": 2,
  "spare_part_status_id": 1,
  "report_date": "2026-08-18",
  "scheduled_execution": "2026-08-18",
  "completed_execution": "2026-08-18",
  "equipment_maintenance_log": "Se cambió el retén de aceite y se probó el motor.",
  "executor_external_id": 22,
  "closed": true
}

RESPONSE 200:
{ "success": true, "message": "Falla cerrada y archivada correctamente." }

═══════════════════════════════════════════════════════════════════════════
EDITAR FALLA SIN CERRAR (flujo aparte, opcional para la app móvil)
═══════════════════════════════════════════════════════════════════════════
Mismo endpoint PUT /api/v1/fallas/{id}, mismos campos base que "Reportar
falla" (sin los campos ⭐ de cierre, sin mandar `closed`). Permiso: "Fallas
Editar". Si la app móvil no va a tener edición simple (solo crear y cerrar),
se puede omitir esta pantalla.

═══════════════════════════════════════════════════════════════════════════
NOTAS / LIMITACIONES ACTUALES DEL BACKEND
═══════════════════════════════════════════════════════════════════════════
- No hay endpoint API todavía para ver el histórico de fallas cerradas
  (existe solo en la web, /historico-fallas). Si la app móvil necesita listar
  fallas ya cerradas, avisar para agregarlo — hoy no está expuesto por API.
- GET /api/v1/fallas (listado) soporta filtro close_status=1 (cerradas) /
  close_status=2 o vacío (abiertas, default) por si se necesita ver el estado
  aunque no el detalle histórico completo.
- Los catálogos de crear-datos NO están paginados (traen todo de una vez) —
  correctos para selects, no usar los endpoints /api/v1/equipos, etc.
  (esos sí paginan a 10 y son para pantallas de administración, no dropdowns).
